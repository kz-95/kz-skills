# 06 - Budget and the session loop - spend it, explain it, improve it

```
PLAN -> RUN -> EXPLAIN -> LEARN -> EXPERIMENT --+
  ^                                          |
  +-------------- next session --------------+
```

**PLAN** - size every task in points; phase budget = `sum points x velocity x 1.2`.
**RUN** - dispatch through check 6; the ledger records est vs actual per task.
**EXPLAIN** - * session report: where tokens went, and *why* it varied.
**LEARN** - `actual / points` -> velocity. A task over 2x est means the **size**
was wrong, so re-size its siblings too.
**EXPERIMENT** - pick ONE change, state the hypothesis, measure it next session.

## Velocity

```
velocity = rolling mean of (actual tokens / points)
```

Kept in `budget/velocity.json`, updated by `pb.py done`. It is the only number
that turns a size into an estimate, so it is worth keeping honest - which is
what rule 10 protects.

## Check 6 - the budget gate

```
est  = points x velocity          <- stored on the task, frozen, unbuffered
need = est x 1.3                  <- the buffer, applied only here
```

**The estimate carries no buffer.** A padded est makes every est-vs-actual
comparison in the ledger lie, and that comparison is the only thing that
re-sizes the DAG. The 1.3 lives at the gate, where it belongs. The 1.2 at plan
time is a separate, phase-level number: a phase plan absorbs variance across
many tasks, a single dispatch does not.

One buffer, three bands:

```
need <= remaining           -> dispatch
est  <= remaining < need    -> dispatch, flag AMBER (it fits, the buffer doesn't)
est  >  remaining          -> hold, then in this order:
      frontier task   -> drop a tier
      pack > 60% of est_in -> trim the context pack
      phase at 80%    -> Musts only
      phase at 100%   -> Ask Card to the user
      still throttled -> checkpoint the DAG, resume next session
```

`est_in` is `est x 0.5` - the share of a task's tokens assumed to be input.
Check 5 enforces the same 60% ceiling at dispatch time, so a pack that would
trigger this rung is usually caught one check earlier.

The order matters. Dropping a tier and trimming the pack are reversible and
cheap; cutting scope is a product decision; asking the user is an interruption.
Do them in that order, not the order that is easiest to automate.

Checkpointing is a normal outcome, not a failure. The DAG, the locks and the
ledger are all on disk, so a session that runs out of budget resumes rather than
restarts.

## The session report

Generated by `pb.py report`, never written by hand. The shape that matters:

```
SESSION 07 - Pre-Production - 18 tasks - 4h12m          (* generated)

spent     412k tokens   vs 380k planned   +8%
points    34 done / 41 planned            83%
velocity  12.1k / point  (was 11.4k)      +6%

WHERE IT WENT                tokens    %   vs est
  o BE-Bruno   api layer      118k   29%   +40%  ^
  o FE-Felix   skeleton        94k   23%    +5%
  * SA-Silas   contracts       71k   17%   -12%
  * CR-Cyrus   review          58k   14%    +2%
  everything else              71k   17%

QUALITY BESIDE COST   (the guardrail - never read the block above alone)
  rework        31k  8% of spend   (changed decisions, pure waste)
  retried       2 task(s) needed a second attempt
  context pack  avg 8.2k in, 18 measured
  CR rejection  - track by hand

WHY IT VARIED  (the half that matters)
  BE +40%      T-12 sized M, behaved XL
               -> re-sized, 3 siblings re-sized too
  rework 31k   D-003 changed mid-session
               -> avoidable, not a velocity problem
  packs        avg 8.2k in - 31% never referenced

TRIED THIS SESSION
  [ok] trim packs to Index + direct deps    -14% input
  [x] drop CR-Cyrus a tier       2 misses, reverted
```

The "where it went" half is arithmetic and the script does it. **The "why it
varied" half is the half that matters and it is written by a model** - a number
without a cause changes nothing next session.

Note how the two causes are treated differently: the +40% is a *sizing* error
that feeds back into the DAG, the 31k of rework is *waste* from a changed
decision and must never be folded into velocity.

## The four levers, best payoff first

1. **Context pack size** - the biggest input lever.
2. **Tier placement** - push work down a tier until it breaks, then stop.
3. **Task granularity** - fixes overrun *and* rework.
4. **Rework rate** - pure waste; chase it to zero.

## The guardrail

**Every cost metric needs a quality metric beside it.** Optimise
tokens-per-point alone and the scheduler will starve agents of context and make
everything cheaper and worse - and the report will look like an improvement
while it happens. Watch CR rejection rate and rework % in the same view, every
session, or the loop eats the project.

## experiments.md

One hypothesis per session. This is the one budget doc a human authors and
reads - but like every shared doc it is *written* by TW-Tessa via `updates/`
(rule 2 has no exceptions). You supply the hypothesis; the scribe files it:

```
S07 - trim packs to Index + direct deps
     expect: -10% input, no change in CR rejection rate
     got:    -14% input, CR rejection 8% -> 9%   [ok] keep
```

**1 session = a signal. 3 sessions = evidence.** Do not change the workflow on
one session's number.
